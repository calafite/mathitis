# Phase 19: Email Verification Hardening, URL Routing Fixes & Custom Error Page

## Objective
Diagnose and resolve the email verification link bug where clicking verification or recovery links lands on `http://localhost:4000/verify-email` returning a raw Fastify `404 Not Found` JSON payload. Implement server-side redirect fallbacks so accidental visits to API-hosted auth paths route seamlessly to the frontend SPA. Finally, implement a dedicated brutalist **Custom Error Page** (matching `not-found.tsx`) that displays full API diagnostic information in a clean, inspectable format rather than raw unformatted JSON or blank screens.

---

## Directives & Platform Constraints
- **URL Disambiguation (Web vs API)**: Fastify API runs on port `4000` (`/api/*`), while the Vite Web SPA runs on port `5173` (or port `80`/`443` through Nginx in production). Email links generated by `auth-mailer.ts` MUST always point to the Web frontend origin.
- **Fail-Safe Server Redirects**: If a user or email client hits `GET /verify-email` or `GET /recover` on the Fastify API (port 4000), Fastify must gracefully `302 Redirect` to the corresponding Web frontend URL with all query parameters preserved.
- **Brutalist Error UX**: Replace default unstyled error fallbacks with a bespoke error page featuring academic brutalist styling, an SVG illustration, and a collapsible "API Diagnostics / Detalhes do Erro" code block showing the full structured API response (`statusCode`, `code`, `message`, `correlationId`).

---

## Tasks

- [ ] **19.1 Dev Environment Web Origin & Mailer Fix (`apps/api`)**
  - **Root Cause**: In `apps/api/src/app.ts`, `webBaseUrl` defaults to `env.PUBLIC_BASE_URL` (`http://localhost:4000`) when `WEB_ORIGIN` is unset in development. As a result, email verification links are minted with port `4000` instead of Vite's port `5173`.
  - In `apps/api/src/app.ts`:
    - Resolve `webBaseUrl` with development awareness:
      ```typescript
      const defaultWebOrigin = env.NODE_ENV === 'development' ? 'http://localhost:5173' : env.PUBLIC_BASE_URL;
      const webBaseUrl = env.WEB_ORIGIN ?? defaultWebOrigin;
      ```
    - Pass this resolved `webBaseUrl` to `createAuthMailer`.

- [ ] **19.2 API Server Root Redirect Fallbacks (`apps/api`)**
  - In `apps/api/src/app.ts` or a new lightweight helper plugin:
    - Register root fallback redirect handlers for top-level browser auth routes hitting the API directly:
      - `GET /verify-email`: Redirects to `${webBaseUrl}/verify-email${queryString}` with HTTP 302.
      - `GET /recover`: Redirects to `${webBaseUrl}/recover${queryString}` with HTTP 302.
      - `GET /reset-password`: Redirects to `${webBaseUrl}/recover${queryString}` with HTTP 302.
    - Ensure query strings (e.g. `?token=...`) are preserved during redirection.

- [ ] **19.3 Email Verification Flow Audit & Correctness Verification (`apps/api` & `apps/web`)**
  - Audit the entire verification sequence:
    1. Registration triggers `authService.register` $\rightarrow$ issues token $\rightarrow$ enqueues email with `${webBaseUrl}/verify-email?token=${token}`.
    2. User clicks link $\rightarrow$ opens `VerifyEmailPage` on the Vite SPA (`/verify-email?token=...`).
    3. `VerifyEmailPage` (`apps/web/src/pages/verify-email.tsx`) reads `searchParams.get('token')` $\rightarrow$ invokes `authApi.verifyEmail(token)` calling `GET /api/auth/verify-email/:token`.
    4. Fastify verifies hash in `user_tokens`, activates the user in `users`, consumes the token, and returns `{ ok: true, message: "E-mail verificado com sucesso" }`.
    5. Frontend displays success confirmation with a direct button to `/login`.
  - Ensure re-verifying an already consumed token is handled idempotently without throwing unhandled 500 errors.

- [ ] **19.4 Brutalist Custom Error Page & Diagnostics Modal (`apps/web`)**
  - Create `apps/web/src/pages/error-page.tsx`:
    - Design a brutalist error page matching `not-found.tsx` (`bg-background`, `border-2 border-foreground`, `font-mono` typography, and stark contrast).
    - Include a custom SVG illustration (e.g., a broken graph edge or fractured circuit).
    - Props/State support: accepts `error: ApiError | Error | unknown`, `title?: string`, `message?: string`, `onRetry?: () => void`.
    - **API Debug Box**: Render a collapsible `<details>` / modal block showing the complete API response:
      ```tsx
      <details className="mt-4 border border-foreground/30 bg-card p-3 font-mono text-xs text-left">
        <summary className="cursor-pointer font-bold uppercase text-primary">
          [+] Detalhes técnicos do erro (API)
        </summary>
        <pre className="mt-2 overflow-x-auto text-[11px] text-foreground/80">
          {JSON.stringify(errorDetails, null, 2)}
        </pre>
      </details>
      ```
    - Action buttons: "Voltar ao início", "Tentar novamente", and "Copiar erro".
  - In `apps/web/src/components/error-boundary.tsx`:
    - Replace the generic unstyled fallback with `<ErrorPage />`.
  - In `apps/web/src/pages/verify-email.tsx`:
    - When verification encounters an error state, use the new error layout with full API error inspection details instead of a flat text string.

- [ ] **19.5 Testing & Automated Quality Gates**
  - **Unit Tests (`apps/api/tests/unit/auth-mailer.test.ts`)**:

  - **Integration Tests (`apps/api/tests/integration/auth.test.ts`)**:
